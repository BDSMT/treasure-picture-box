# 藏图盒 · 插件化重构方案（v1.3.0 路线）

> 本文是基于**当前真实代码**（`ui/app.py` 1434 行、`core/` 10 个模块、`build.py` 单包打包）给出的落地方案，
> 不是架构空谈。每个设计决策都标注了它解决的具体问题，以及为什么不用别的做法。

---

## 0. 现状诊断：为什么不能「直接拆」

### 0.1 事实清单（探查结果）

| 事实 | 位置 | 对重构的意义 |
|---|---|---|
| 5 个模块用 `if self.tab == "seed" / elif ...` 硬编码分发 | `ui/app.py:194-203` | 必须换成注册表驱动 |
| 每切一次 tab 就 `destroy()` 全部控件重建 | `ui/app.py:145-146` | **利好**：模块 UI 天然是「状态 → 控件」纯映射，可直接抽象为插件方法 |
| 模块状态外置在 `self.st_seed / st_un / st_pt / st_ex / st_cu` | `ui/app.py:128-134` | 状态已经和控件解耦，迁移时只需搬到插件对象上 |
| **全程同步执行，无 threading** | 全文件仅 3 处 `after(60, ...)` 用于防抖 | **最大缺口**：处理时界面冻结，无转圈图标 |
| 图种从未压缩过载荷 | `core/seed.py:45` `pack()` 只做字节追加 | 「内置 7-Zip 压缩」是**新增能力**，不是改造 |
| `zipfix` 已在做中央目录偏移修正 | `core/zipfix.py:84-100` | 这正是「二次压缩破坏完整性」的技术根源（见 §4.5） |
| `matting` 依赖 cv2 + onnxruntime ≈ 106 MB | `core/matting.py:22-23` | 拆分收益的全部来源 |

### 0.2 三个结构性障碍

**障碍一：`ui/app.py` 是上帝类。**
1434 行里塞了 5 个模块的建界面、状态刷新、文件读写、错误提示。拆插件不是「搬文件」，是**先把这个类拆成「框架」和「模块」两层**。

**障碍二：模块之间靠 `self` 隐式耦合。**
`build_seed()` 里调 `self.toast()`、`self._pick()`、`self._refs.append()`。插件拿不到 `self`，必须有一个**显式的能力接口**把这些交出去（见 §2.7 的 `HostContext`）。

**障碍三：PyInstaller onedir 不支持「运行时随便 import 新模块」。**
打包后 `sys.path` 固定在 `_internal/`，动态 import 未收集的模块会失败。所以「插件独立打包」必须给每个插件**自己的依赖目录**，不能共享本体（见 §3.4）。

### 0.3 拆分收益量化

当前包 64.4 MB（压缩后）。按依赖拓扑拆开后：

| 包 | 内容 | 预估体积（压缩后） |
|---|---|---|
| 本体 | 框架 + seed（图种） | **≈ 14–18 MB** |
| `unpack` 插件 | 标准库 + zipfix/sniff | **< 1 MB** |
| `phantom` 插件 | numpy + PIL | ≈ 12 MB（与 reveal 共享 numpy 时可去重） |
| `reveal` 插件 | numpy + PIL | ≈ 12 MB |
| `matting` 插件 | numpy + **cv2 + onnxruntime** | **≈ 38 MB** |

**结论**：用户只想要图种功能时，下载量从 64.4 MB 降到约 16 MB —— 这就是这次重构唯一的、也是充分的理由。

## 1. 版本路线：为什么必须分两步

用户的要求是「1.2.0 只发插件包、1.3.0 才真正拆分」。这个顺序不是随意定的，它恰好对应两种风险等级的改造：

### 1.2.x —— 双轨期（建机制，不拆身）

- **本体**：仍然包含全部 5 个模块，界面不变，用户无感。
- **同时引入**：插件注册表、`HostContext`、`TaskRunner`、转圈图标。
- **新增功能一律以插件包形式发布**，不再出完整包。
- **目的**：在「有完整功能兜底」的前提下验证插件机制。插件加载失败时能退回内置模块，不会让用户白屏。

> 一句话：**先把插座装好，电器还是原来的**。

### 1.3.0 —— 收口期（拆身）

- 本体只留 `seed`（图种）。
- 其余 4 个模块变成独立插件包，每包可单独安装/卸载。
- 完整包 = 本体 + 5 个插件（一键装），精简包 = 只有本体。
- **API 版本锁定**：`api_version = "1.0"`，1.3.x 内不变，保证插件向后兼容。

### 为什么不能一步到位

`ui/app.py` 有 1434 行、5 套高度同构但细节不同的 UI 逻辑。一次性拆干净，任何一处 `self.xxx` 漏改都会让某个模块在打包后才崩（PyInstaller 不报 import 错，只在运行时 `AttributeError`）。分两步，第一步留兜底，第二步才敢删。

## 2. 插件加载机制

### 2.1 插件契约

不做基类继承，用 **`Protocol` + 鸭子类型**。理由：插件可以被第三方写，不该强制他们 import 本体的类（版本耦合）。

```python
# cangtu/api.py —— 宿主与插件之间的唯一契约
from typing import Protocol, Optional
import tkinter as tk

API_VERSION = "1.0"

class Plugin(Protocol):
    # ── 元数据（静态声明，不需要构造实例就能读）──
    id: str            # 唯一标识："seed" / "unpack" / "phantom" / "reveal" / "cut"
    name: str          # 侧栏主标题："抠图"
    subtitle: str      # 侧栏副标题："主体分离 · 三视图"
    order: int         # 侧栏排序，10/20/30/...
    api_version: str   # 兼容的宿主 API 版本
    requires: list[str]  # 依赖的其他插件 id（如 unpack 依赖 seed 的 zipfix 常量）

    # ── 生命周期 ──
    def check(self) -> tuple[bool, str]:
        """可用性自检。返回 (可用, 不可用原因)。

        在侧栏渲染时调用，不可用的插件显示为灰色 + 原因，
        而不是让用户点进去才报错。
        典型用途：matting 检查 cv2/onnxruntime 是否在插件 vendor 里。
        """

    def build(self, ctx: "HostContext") -> tk.Frame:
        """构建并返回该模块的根控件。

        必须在 ctx.stage 里或作为其子控件创建。
        切 tab 时宿主会 destroy 掉上一次返回的 Frame，
        所以这里**不能**缓存控件引用 —— 一切状态放 self。
        """
```

**为什么 `build` 返回 Frame 而不是继承 App**：
现有架构每次切 tab 都全量重建（`ui/app.py:145`）。如果插件继承 App，切 tab 时的 destroy/重建逻辑就要复制到每个插件里。返回 Frame 让宿主统一管理生命周期，插件只负责「给我一块画布，我画完还你」。

### 2.2 目录与清单

```text
cangtu-box/
├── 藏图盒.exe
├── _internal/              # 本体运行时
├── plugins/
│   ├── manifest.json       # 已安装插件清单（决定侧栏顺序与启用状态）
│   ├── unpack/
│   │   ├── plugin.py       # 入口：必须有 PLUGIN 变量
│   │   ├── vendor/         # 该插件私有的第三方依赖（可选）
│   │   └── plugin.json     # 元数据副本（供不加载代码就能读）
│   ├── phantom/
│   ├── reveal/
│   └── cut/
└── models/                 # 抠图模型（cut 插件专用）
```

`manifest.json`：

```json
{
  "api_version": "1.0",
  "plugins": [
    {"id": "unpack",  "dir": "plugins/unpack",  "enabled": true, "installed_at": "2026-11-11T20:00:00"},
    {"id": "cut",     "dir": "plugins/cut",     "enabled": true, "installed_at": "2026-11-11T20:01:00"}
  ]

```

**为什么 manifest 和 plugin.json 两份**：
- `manifest.json` 是**安装状态**（宿主写，卸载时删条目）
- `plugin.json` 是**插件自述**（插件包自带，安装前就能读，用于「安装预览」显示名称/大小/依赖）

### 2.3 发现：不 import 就能读取

这是「按需加载」的关键——如果为了在侧栏显示插件名而 import 所有插件，那 `matting` 的 `import cv2` 会在启动时发生，按需加载就失效了。

```python
# cangtu/loader.py
import json
from pathlib import Path

def discover(root: Path) -> list[PluginMeta]:
    """扫描 plugins/，只读 JSON，不 import 任何插件代码。"""
    out = []
    for pj in sorted(root.glob("plugins/*/plugin.json")):
        try:
            meta = json.loads(pj.read_text(encoding="utf-8"))
        except Exception:
            continue
        meta["dir"] = str(pj.parent)
        out.append(PluginMeta(**meta))
    return out
```

侧栏渲染只用 `PluginMeta`（名称、图标、顺序），**零 import、零依赖**。

### 2.4 按需加载：首次切到才 import

```python
def load_plugin(meta: PluginMeta) -> Plugin:
    """真正 import 插件代码。只在用户第一次点进该 tab 时调用。"""
    dirp = Path(meta.dir)
    # 插件私有依赖优先
    vendor = dirp / "vendor"
    if vendor.is_dir() and str(vendor) not in sys.path:
        sys.path.insert(0, str(vendor))
    # 用目录名做包名，避免和本体 core 冲突
    spec = importlib.util.spec_from_file_location(
        "_cangtu_plugin_" + meta.id, dirp / "plugin.py"
    )
    mod = importlib.util.module_from_spec(spec)
    spec.loader.exec_module(mod)      # ← 这一刻才 import cv2 / onnxruntime
    return mod.PLUGIN
```

**加载时机**：`App._switch(tab)` 里判断 `if tab not in self._loaded: self._loaded[tab] = load_plugin(...)`。

**加载失败的兜底**（1.2.x 双轨期特有）：若 `load_plugin` 抛异常，退回内置模块并 toast 提示。1.3.0 后无内置模块，则显示错误占位页 + 「该插件不可用」说明。

### 2.5 卸载

运行期卸载（不重启）：

```python
def unload(self, pid: str):
    self._loaded.pop(pid, None)                  # 丢引用
    for m in list(sys.modules):
        if m.startswith("_cangtu_plugin_" + pid):
            sys.modules.pop(m, None)             # 清模块缓存
    vendor = str(Path(self._meta[pid].dir) / "vendor")
    if vendor in sys.path:
        sys.path.remove(vendor)
```

安装期卸载（真正删除）：

```python
def uninstall(self, pid: str):
    self.unload(pid)
    shutil.rmtree(Path(self._meta[pid].dir))     # 删插件目录
    self.manifest.pop(pid)                        # 删清单条目
    self.manifest.save()
```

**注意**：`sys.modules` 里已 import 的 `cv2` 不会因为卸载插件而释放（Python 不回收模块内存）。这没关系——卸载后不再使用即可，下次启动不会加载。

### 2.6 依赖管理

**原则：插件自带依赖，不污染本体。**

| 场景 | 做法 |
|---|---|
| 插件依赖本体已有的库（numpy/PIL） | 直接 `import`，本体 `_internal/` 里有 |
| 插件依赖本体没有的库（cv2/onnxruntime） | 打包时 `pip install --target plugins/cut/vendor`，加载时插 `sys.path` |
| 插件依赖另一个插件（如 unpack 想复用 zipfix） | **不允许**直接 import 别的插件。共用逻辑应上移到本体 `cangtu/common/` |

`zipfix` / `sniff` 这两个是 seed 和 unpack 共用的，必须留在**本体**而不是某个插件里——这决定了 §3 的拆分边界。

### 2.7 宿主上下文 HostContext —— 插件唯一能碰到的本体

插件不继承 App，但需要 App 的能力。全部通过一个显式的 `ctx` 对象传递：

```python
# cangtu/api.py
class HostContext:
    # 外观
    pal: dict            # 调色板（随主题切换）
    def s(self, n: int) -> int: ...          # DPI 缩放
    # 通用能力
    def toast(self, text: str, err: bool = False): ...
    def pick_file(self, cb, images_only=False, title="选择文件"): ...
    def ask_save(self, default_name: str, ext: str) -> Optional[Path]: ...
    def ask_confirm(self, title: str, message: str, danger: bool = False) -> bool: ...
    # 状态与并发（见 §5）
    tasks: TaskRunner
    # 共享服务
    seven_zip: "SevenZip"     # 7-Zip 封装（见 §4）
    config: dict
    # 控件库（复用本体 widgets，保证视觉一致）
    widgets: types.ModuleType
```

**为什么用对象而不是全局变量**：插件要能单独测试。传 `ctx` 的 mock 就能在无窗口环境跑单测。

## 3. 模块拆分边界

### 3.1 依赖拓扑（决定边界）

```text
cangtu/common/            ← 本体，所有插件可依赖
├── paths.py              （路径、配置、日志）
├── imageio.py            （PIL 封装：open_rgba / fit_contain / save_png）
├── sniff.py              （字节流格式识别）
└── zipfix.py             （ZIP 偏移修正）★ seed 与 unpack 共用，必须留本体

plugins/seed/   （本体内置，不单独成包）
└── 依赖 common/zipfix, common/sniff, common/imageio

plugins/unpack/ → common/zipfix, common/sniff
plugins/phantom/→ common/imageio + numpy, PIL
plugins/reveal/ → numpy, PIL
plugins/cut/    → numpy, cv2, onnxruntime（自带 vendor）★ 重依赖，独立包的全部理由
```

**边界判据**（三条，按优先级）：
1. **被两个以上模块使用的 → 留本体**（zipfix/sniff/imageio/paths）
2. **带重依赖的 → 必须独立**（cut 的 cv2/onnxruntime）
3. **有独立用户价值的 → 独立**（unpack 是「不用改后缀就能看压缩包」，本身就是卖点）

### 3.2 五个插件的职责与接口

| 插件 | id | 职责 | 核心 API（内部） |
|---|---|---|---|
| 图种 | `seed` | 图片 + 载荷 → 图种；拆分图种 | `pack() / split() / write()` + **新增 `compress_payload()`** |
| 图种解包 | `unpack` | 图种 → 文件列表 / 导出 / torrent | `detect() / zip_entries() / torrent_info()` |
| 幻影坦克 | `phantom` | 两图 → 一图双画面 | `compose() / advice()` |
| 幻影提取 | `reveal` | 双画面 → 拆回两图 | `analyze() / auto_reveal() / build_fg() / build_bg()` |
| 抠图 | `cut` | 主体分离 + 三视图 | `cut() / layers() / compose()` |

**每个插件的标准骨架**（5 个方法，对应现在 `app.py` 里的 4 类方法）：

### 3.4 独立打包方案

**问题**：PyInstaller onedir 打完，`_internal/` 是一个封闭环境，动态 import 不进去。

**方案**：本体和每个插件**各自打一次**，插件产物是「一个文件夹」，放进 `plugins/` 即可被加载。

```python
# build.py 新增：单插件打包
def build_plugin(pid: str):
    spec = build_plugin_spec(pid)     # 动态生成 .spec
    run_pyinstaller(spec, outdir=ROOT / "dist_plugins" / pid)
```

插件 `.spec` 的关键差异：

```python
# 插件不 EXE，只 COLLECT 成一个目录（供本体 import）
a = Analysis([plugin_entry], ...)
pyz = PYZ(a.pure)
coll = COLLECT(pyz, a.binaries, a.datas, name=pid)   # 无 EXE
```

插件目录结构（打完后）：

```text
dist_plugins/cut/
├── plugin.py            # 源（未打包时直接可用）
├── plugin.json
├── _internal/           # 该插件私有的 DLL / pyd
│   ├── cv2/  (72 MB)
│   └── onnxruntime/ (34 MB)
└── vendor/              # pip --target 装的纯 Python 包
```

加载时把 `插件目录/_internal` 和 `插件目录/vendor` 都插入 `sys.path`，`cv2` 就能 import。

**打包产出的两种分发形态**：

| 形态 | 内容 | 用途 |
|---|---|---|
| 完整包 | 本体 + 全部 5 插件 | 新用户，一次装好 |
| 精简包 | 只有本体（seed） | 只要图种功能，约 16 MB |
| 插件包 | 单个 `plugins/xxx/` 目录的 zip | 老用户增量安装 |

**安装插件的用户体验**：拖一个 `cut-plugin-v1.0.zip` 到程序窗口 → 解压到 `plugins/cut/` → 写 manifest → 侧栏立刻出现新 tab。

### 3.5 迁移顺序（降低风险）

1. **抽 `HostContext`**：先在现有 `App` 上加这层，内部直接转发到 `self.xxx`，行为零变化。
2. **迁 `unpack`**（依赖最轻、无 AI）：验证插件机制的最小闭环。
3. **迁 `phantom` / `reveal`**（共用 imageio，验证依赖共享）。
4. **迁 `cut`**（验证重依赖 vendor 加载）。
5. **迁 `seed` 到 `plugins/seed/`**（本体内置，但走同一套接口）。
6. **删掉 `app.py` 里的旧 `build_xxx()`**，1434 行降到约 250 行。

## 4. 压缩处理流程（7-Zip）

### 4.1 内置 7-Zip 的接入方式

**现状**：本机 `C:\Program Files\7-Zip\7z.exe` 不存在，`PATH` 里也没有 `7z`。所以**必须内置**。

**选型**：内置官方独立版 `7za.exe`（约 1.5 MB）。

| 候选 | 大小 | 支持格式 | 结论 |
|---|---|---|---|
| `7zr.exe` | 0.6 MB | 仅 7z | ❌ 不能识别 zip 以外的包 |
| **`7za.exe`** | **1.5 MB** | 7z/zip/tar/gz/bz2/xz | ✅ **选它** |
| `7z.exe` + `7z.dll` | 2.5 MB | 加 rar 解压 | 冗余，见下 |

**为什么不支持 rar**：我们只需要「识别格式」和「压缩成 7z」，不需要解压 rar。识别 rar 用魔数 `Rar!\x1a\x07` 就够了（`sniff.guess_type` 已能做）。所以 `7za.exe` 足够。

**分发合规**：7-Zip 是 LGPL + unRAR 限制条款。随程序分发 `7za.exe` 需要在「关于」里注明来源与许可，附上 `License.txt`。

```python
# cangtu/sevenzip.py
import subprocess, sys
from pathlib import Path

CREATE_NO_WINDOW = 0x08000000

class SevenZip:
    def __init__(self, exe: Path):
        self.exe = exe

    def available(self) -> bool:
        return self.exe.is_file()

    def version(self) -> str:
        r = subprocess.run([str(self.exe)], capture_output=True,
                           creationflags=CREATE_NO_WINDOW)
        return r.stdout.decode("utf-8", "replace").splitlines()[1] if r.stdout else ""

    def compress(self, sources: list[Path], out: Path, level: int = 5,
                 progress=None) -> Path:
        """压成 .7z。level 0=仅存储 5=标准 9=极限。"""
        cmd = [str(self.exe), "a", "-t7z", "-mx=%d" % level, "-y", str(out)]
        cmd += [str(p) for p in sources]
        r = subprocess.run(cmd, capture_output=True,
                           creationflags=CREATE_NO_WINDOW)
        # 7-Zip 返回 0=成功 1=有警告（如部分文件被跳过），都算可用
        if r.returncode not in (0, 1):
            raise CompressionError(r.stderr.decode("utf-8", "replace") or
                                   r.stdout.decode("utf-8", "replace"))
        return out

    def list_formats(self) -> set[str]:
        """解析 `7z i`，拿到它能解的格式，用于校验识别结果。"""
        r = subprocess.run([str(self.exe), "i"], capture_output=True,
                           creationflags=CREATE_NO_WINDOW)
        text = r.stdout.decode("utf-8", "replace")
        return {ln.split()[0] for ln in text.splitlines()
                if ln.strip() and not ln.startswith(" ") and " " in ln}
```

**关键细节**：`creationflags=CREATE_NO_WINDOW` —— 不加的话，GUI 程序调 `7za.exe` 会闪一个黑框（和 `console=False` 打包的初衷冲突）。

### 4.2 格式识别

复用现有的 `core/sniff.py:guess_type()`，它已经能认 PNG/JPEG/GIF/ZIP/RAR/7Z/TAR/GZ 等。补充一个「是否可作为图种载荷」的判定：

```python
def classify_payload(path: Path) -> tuple[str, str]:
    """返回 (类别, 具体格式)。

    类别：
      'archive'  —— 压缩包（zip/7z/rar/tar/gz），可直接当载荷
      'image'    —— 图片（jpg/png/gif），原样移入，不压缩
      'other'    —— 普通文件，需询问是否压缩
    """
    head = path.open("rb").read(512)
    hit = sniff.guess_type(head)
    kind = hit[0] if hit else "未知"

    if kind in ("ZIP", "RAR", "7Z", "TAR", "GZ", "BZ2", "XZ"):
        return "archive", kind
    if kind in ("PNG", "JPEG", "GIF", "BMP", "WEBP"):
        return "image", kind
    return "other", kind
```

### 4.4 三类弹窗的触发条件（精确）

| 弹窗 | 触发条件 | 文案要点 | 危险级 |
|---|---|---|---|
| **A · 二次压缩风险** | `classify == 'archive'` **且** `risk_second_compress() == True` | 「这个文件本身是图种（图片 + 内嵌 ZIP）。再压缩会让内嵌 ZIP 的中央目录偏移错位，拆开后会打不开。确定要继续吗？」 | ⚠ 高（红色按钮） |
| **B · 非压缩包询问** | `classify == 'other'` | 「这不是压缩包（识别为 X）。要先压成 .7z 再藏吗？不压缩的话藏进去会比较大。」 | 普通 |
| **C · 结果说明** | 载荷是 ZIP 且 `patched == True` | 「已对 ZIP 偏移做修正（+N 字节），这样 7-Zip / 资源管理器也能直接解压。」 | 信息 |

**弹窗 A 的判定逻辑**（技术核心）：

```python
def risk_second_compress(payload: bytes) -> tuple[bool, str]:
    """图种 = 图片字节 + 已偏移修正的 ZIP。

    对图种再压缩，7-Zip 会把它当普通文件打包（无害），但如果用户
    用 7-Zip 的「智能识别」去重新打包内部 ZIP，中央目录偏移会二次错位。
    这里保守判定：只要检测到「ZIP 前面挂着非 ZIP 数据」就提示。
    """
    # 情况一：本身是 ZIP，但 EOCD 里记录的偏移和实际位置不一致
    # 注：用公开的 describe()（返回 dev 字段），不要碰私有的 _layout()
    if zipfix.is_zip(payload):
        info = zipfix.describe(payload)
        if info and info.get("dev", 0) > 0:
            return True, ("这个 ZIP 前面挂着 %d 字节的非 ZIP 数据（图种特征）。"
                          "二次压缩会让偏移再次错位。" % info["dev"])
        return False, ""

    # 情况二：开头是图片，但中间夹着 ZIP 签名 → 是图种
    head = sniff.sniff(payload[:64])
    if head and head.kind in ("PNG", "JPEG", "GIF"):
        if b"PK\x03\x04" in payload:
            return True, "这是图种（图片 + 内嵌 ZIP），再压缩会破坏内嵌 ZIP 的偏移。"
    return False, ""
```

### 4.5 为什么「二次压缩」真的会坏（原理）

这部分值得讲清楚，因为它决定了弹窗不是「多此一举的确认」。

ZIP 的中央目录（Central Directory）里，每个条目都记着「本地文件头相对**文件开头**的偏移」。图种的构造是：

```
[ 图片字节 (N 字节) ][ ZIP 全部内容 ]
                     ↑ 这里开始才是 ZIP 的「文件开头」
```

但 ZIP 内部记录的偏移是「相对 ZIP 自身起点」的。所以 `zipfix.fix_prefix()` 把每个条目的偏移 **+N**（`core/zipfix.py:94` `new = lho + delta`），这样 7-Zip 从整个文件的第 0 字节读数时，加上 N 刚好落在正确的本地文件头位置。

**如果对这个图种再压一次**：7-Zip 把「图片 + ZIP」整个当输入，如果它识别出内部有 ZIP 并尝试「优化」，会重新计算所有偏移——它不知道这 N 字节是刻意加的，重算后就又回到了「相对 ZIP 起点」，而文件开头仍是图片。结果：解压器从第 0 字节读，偏移全部错位 N 字节，报「不是有效压缩文件」。

**这就是「二次压缩破坏原文件完整性」的确切含义**，不是玄学。

### 5.2 TaskRunner —— 统一的任务与状态管理

```python
# cangtu/tasks.py
import threading
from dataclasses import dataclass, field

@dataclass
class TaskState:
    status: str = "idle"        # idle | loading | done | error
    message: str = ""
    gen: int = 0                # 代数，用于丢弃过期结果

class TaskRunner:
    """所有插件共用的异步执行器。

    设计要点：
    - 一个 key 同一时刻只允许一个任务；新任务让旧任务的结果作废（gen 不匹配就丢）
    - 结果回到 Tk 主线程（after(0, ...)），插件里不用自己管线程安全
    - 每个 key 挂一个 spinner，状态变化时自动 start/stop
    """

    def __init__(self, root):
        self.root = root
        self._states: dict[str, TaskState] = {}
        self._spinners: dict[str, object] = {}

    def state(self, key: str) -> TaskState:
        return self._states.setdefault(key, TaskState())

    def attach_spinner(self, key: str, sp):
        self._spinners[key] = sp

    def submit(self, key, fn, on_ok, on_err=None):
        st = self.state(key)
        st.gen += 1
        gen = st.gen
        st.status, st.message = "loading", ""
        sp = self._spinners.get(key)
        if sp: sp.start()

        def worker():
            try:
                res = fn()
            except Exception as exc:      # noqa: BLE001
                self.root.after(0, lambda: self._finish(key, gen, None, exc, on_ok, on_err))
            else:
                self.root.after(0, lambda: self._finish(key, gen, res, None, on_ok, on_err))

        threading.Thread(target=worker, daemon=True).start()

    def _finish(self, key, gen, res, exc, on_ok, on_err):
        st = self.state(key)
        if st.gen != gen:
            return                      # 已被更新的任务取代，静默丢弃
        sp = self._spinners.get(key)
        if sp: sp.stop()
        if exc is not None:
            st.status, st.message = "error", str(exc)
            if on_err: on_err(exc)
        else:
            st.status = "done"
            on_ok(res)
```

**为什么用 `gen` 代数而不是 `cancel()`**：Python 线程无法强制中断。用户快速换图时，旧任务还会跑完，只是结果被丢弃。这比试图 kill 线程简单可靠得多（也避免了 Tkinter 跨线程崩溃）。

### 5.3 转圈图标 Spinner

```python
# cangtu/spinner.py
import tkinter as tk

class Spinner(tk.Canvas):
    def __init__(self, master, size=20, color="#7A7A85", bg="#000000", **kw):
        super().__init__(master, width=size, height=size, bg=bg,
                         highlightthickness=0, bd=0, **kw)
        self._n, self._color, self._size = 8, color, size
        self._ang = 0
        self._job = None
        self._items = []
        self._paint()

    def set_colors(self, color, bg):
        self._color = color
        self.configure(bg=bg)
        self._paint()

    def _paint(self):
        for it in self._items:
            self.delete(it)
        self._items.clear()
        size, n = self._size, self._n
        pad = 3
        box = (pad, pad, size - pad, size - pad)
        for i in range(n):
            # 越靠前的段越不透明，形成拖尾
            shade = 0.15 + 0.85 * (i / max(1, n - 1))
            col = _blend(self._color, self._bg_rgb(), shade)
            start = self._ang + i * (360 / n)
            self._items.append(self.create_arc(
                *box, start=start, extent=360 / n - 6,
                style="arc", outline=col, width=2))

    def start(self):
        if self._job is None:
            self.place(relx=0.5, rely=0.5, anchor="center")   # 或 grid/pack
            self._tick()

    def _tick(self):
        self._ang = (self._ang + 45) % 360
        self._paint()
        self._job = self.after(90, self._tick)

    def stop(self):
        if self._job is not None:
            self.after_cancel(self._job)
            self._job = None
        self.place_forget()      # ← 「处理结束后自动移除」
```

**关键行为**：`stop()` 里 `place_forget()` —— 这就是用户要的「处理结束后自动移除」。

## 6. 抠图改进：先轮廓、后抠图

### 6.1 问题归因：四个现象 → 四个根因

| 用户反馈的现象 | 根因（对照现有代码） |
|---|---|
| **四肢存在半透明** | `_refine_alpha()`（`matting.py:223`）用引导滤波对整张 mask 做平滑，四肢边缘的软概率被扩散成 0.2~0.8 的渐变带，整块变半透明 |
| **边界不清晰时效果差** | AI mask 在低对比度边界处概率平缓（0.4~0.6），`_ai_mask` 双三次上采样后更糊，阈值 0.5 切开的位置漂移 |
| **重复使用颜色** | `_grow_bg()` 用颜色连通性判断背景，背景里与主体同色的元素会被一起当成背景删掉（或反过来） |
| **阴影** | 阴影是「主体色的暗版本」，颜色上与主体连续，区域生长会跨过阴影吃掉主体边缘，或把阴影留在前景 |

**共同本质**：现在的方法**全靠颜色相似度**做全局判断。颜色一重复、一有阴影，判断就失去依据。

### 6.2 改进思路：用几何约束替代全局颜色判断

用户提的「先基于边缘轮廓处理、再执行抠图」，技术上对应的是 **trimap 驱动的窄带抠图（Narrow-band Matting）**，标准做法：

> 先用**几何**（边缘 + 轮廓闭合）确定「主体的大致边界在哪」，
> 然后**只在边界附近的窄带里**做颜色采样和软 alpha 估计。

好处是：窄带之外的区域是**确定的**（要么全前景要么全背景），半透明只可能出现在窄带里。四肢内部的像素根本不会被算成 0.3 —— 从根上消除了「四肢整体半透明」。

### 6.3 三阶段算法

#### 阶段一：轮廓提取（不看颜色）

```python
def _contour_mask(img: np.ndarray) -> np.ndarray | None:
    """几何轮廓。完全不依赖颜色相似度，所以阴影/重复色不会干扰。"""
    gray = cv2.cvtColor(img, cv2.COLOR_BGR2GRAY)

    # 1) 自适应 Canny：阈值跟中位数走，深色图和浅色图都能用
    med = float(np.median(gray))
    lo, hi = int(max(0, 0.66 * med)), int(min(255, 1.33 * med))
    edges = cv2.Canny(gray, lo, hi)

    # 2) 闭运算把断开的轮廓连起来（漫画线稿常有 1~3 px 断裂）
    k = cv2.getStructuringElement(cv2.MORPH_ELLIPSE, (5, 5))
    closed = cv2.morphologyEx(edges, cv2.MORPH_CLOSE, k, iterations=2)

    # 3) 取最大闭合轮廓作为主体
    cnts, _ = cv2.findContours(closed, cv2.RETR_EXTERNAL, cv2.CHAIN_APPROX_SIMPLE)
    if not cnts:
        return None
    cnt = max(cnts, key=cv2.contourArea)
    if cv2.contourArea(cnt) < gray.size * 0.02:      # 太小，不可信
        return None

    mask = np.zeros(gray.shape, np.uint8)
    cv2.drawContours(mask, [cnt], -1, 255, thickness=-1)
    return _fill_holes(mask)      # 复用现有的填孔（已修好边界判定）
```

**为什么用「最大轮廓」**：二次元立绘的主体通常是画面中面积最大的连通轮廓。这比颜色更稳——背景花纹再花哨，也不会形成比人物更大的闭合轮廓。

#### 阶段二：窄带软 alpha（只在边界附近算）

```python
def _band_alpha(img, hard_mask, band: int = 9) -> np.ndarray:
    """只在 hard_mask 边界内外各 band 像素的窄带里做软 alpha。

    窄带外：内部=1.0，外部=0.0。四肢内部永远不会被算成半透明。
    """
    k3 = cv2.getStructuringElement(cv2.MORPH_ELLIPSE, (3, 3))
    k9 = cv2.getStructuringElement(cv2.MORPH_ELLIPSE,
                                   (band * 2 + 1, band * 2 + 1))

    sure_fg = cv2.erode(hard_mask, k3, iterations=2)      # 确定前景
    sure_bg = cv2.bitwise_not(cv2.dilate(hard_mask, k9))  # 确定背景
    band_area = cv2.bitwise_not(cv2.bitwise_or(sure_fg, sure_bg))

    alpha = np.zeros(hard_mask.shape, np.float32)
    alpha[sure_fg > 0] = 1.0

    # 在窄带里用「到前景/背景的距离」做初估，再用引导滤波对齐边缘
    dist_in = cv2.distanceTransform(hard_mask, cv2.DIST_L2, 3)
    dist_out = cv2.distanceTransform(255 - hard_mask, cv2.DIST_L2, 3)
    est = dist_in / (dist_in + dist_out + 1e-6)           # 0..1 平滑过渡
    est = np.clip((est - 0.5) * 2 + 0.5, 0, 1)            # 提高对比

    sel = band_area > 0
    alpha[sel] = _guided(cv2.cvtColor(img, cv2.COLOR_BGR2GRAY),
                         est.astype(np.float32), r=8, eps=1e-3)[sel]
    return alpha
```

#### 阶段三：半透明修正（专治四肢）

```python
def _fix_translucent(alpha, min_ratio: float = 0.002) -> np.ndarray:
    """找出「大块半透明」并强制二值化。

    判据：面积够大 + 形状是块状（不是细长）。
    发丝是细长的，保留软边；四肢是块状的，硬边化。
    """
    mid = ((alpha > 0.2) & (alpha < 0.8)).astype(np.uint8)
    n, lab, stats, _ = cv2.connectedComponentsWithStats(mid, 8)
    total = alpha.size

    for i in range(1, n):
        area = stats[i, cv2.CC_STAT_AREA]
        if area < total * min_ratio:
            continue                                   # 小碎块：可能是真发丝，放过
        w, h = stats[i, cv2.CC_STAT_WIDTH], stats[i, cv2.CC_STAT_HEIGHT]
        aspect = max(w, h) / max(1, min(w, h))
        solidity = area / max(1, w * h)
        if aspect < 3.0 or solidity > 0.5:             # 块状 → 四肢/躯干
            m = lab == i
            alpha[m] = (alpha[m] > 0.5).astype(np.float32)
    return alpha
```

**三个阈值的依据**：
- `0.2 ~ 0.8`：标准的「可疑半透明」区间。`<0.2` 当背景，`>0.8` 当前景。
- `aspect < 3`：长宽比小于 3 说明不是细长结构，不可能是单根发丝。
- `solidity > 0.5`：实心度（面积/外接矩形）大于 0.5 是块状。

#### 主流程改造

```python
def cut(path, use_ai=True, max_side=0):

    # 1) AI 给软 mask（若有模型）
```

`_merge_masks` 的策略：

```python
def _merge_masks(ai_prob, contour_mask):
    """AI 定主体归属，轮廓修边界形态。

    - 两者的交集必属前景（双重确认）
    - 轮廓内、AI 概率中等（0.3~0.5）的 → 归前景（AI 保守但几何确定）
    - AI 概率高但轮廓外的 → 保留（可能是抠出的发丝探出轮廓）
    """
    hard = (ai_prob > 0.5) | (contour_mask > 0)
    inner = (contour_mask > 0) & (ai_prob > 0.3)
    hard |= inner
    return _fill_holes(hard.astype(np.uint8) * 255) > 0
```

### 6.4 预期改善对照

| 场景 | 现在 | 改进后 |
|---|---|---|
| 四肢半透明 | 整块 0.3~0.7 | 窄带外强制 1.0，只在边缘 9 px 内软过渡 |
| 边界不清晰 | 阈值 0.5 位置漂移 | 几何轮廓定位，边缘由 Canny 决定 |
| 背景重复色 | 被一起吃掉 | 轮廓内部一律前景，不看颜色 |
| 阴影 | 吃到主体边缘 | 轮廓不闭合处由 AI 补，阴影在轮廓外 |
| 发丝 | 软边（保留） | 软边（`aspect>3` 跳过二值化，保留） |

**代价**：每张图多一次 Canny + distanceTransform + connectedComponents，实测约 +80~150 ms（在 2.5 s 的 AI 推理面前可忽略）。

## 8. 风险与回退

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| PyInstaller 打包插件后动态 import 失败 | 中 | 插件不可用 | P3 先在**源码模式**验证，再打包；每插件目录插 `sys.path` 而非依赖 `_internal` |
| `sys.modules` 污染（插件 A 和 B 装了不同版本 numpy） | 低 | 冲突 | 约定：numpy/PIL 只用本体的，插件 vendor 只放本体没有的库 |
| 1.3.0 删内置模块后发现某插件有隐藏依赖 | 中 | 功能缺失 | 1.2.x 双轨期至少跑满 4 个插件版本再收口 |
| 7-Zip（LGPL）分发合规 | 低 | 法务 | 附 `License.txt`，About 里注明版本与来源 |
| 转圈在 Tk 主线程卡顿 | 低 | 动画不顺 | spinner 用 `after(90)` 而非 `after(16)`，本身开销极小；重活在 worker 线程 |
| 轮廓法在「主体不唯一」的图上误判 | 中 | 抠错 | `_merge_masks` 要求 AI 与轮廓双确认；无 AI 时轮廓面积过小（<2%）直接放弃走 basic |

**总回退策略**：1.2.x 全程保持双轨（内置模块 + 插件机制并存），任何一个插件出问题，删掉 `plugins/xxx/` 就退回内置版。**只有 P8 是不可逆的**，放在最后，且前面 7 个阶段都验证过才做。
